# Pre-market-run audit — `feat/market-run`, 2026-08-25

Scope: what is still broken or still slow *before* the 30-merchant run is built on
top of it. Ranked by blast radius, not likelihood. Every performance claim carries
a measurement taken on this machine; every correctness claim was reproduced against
the merged source with a faked Razorpay client and a scripted provider (no network,
`.env` untouched).

**Verdict: fix first.** The system is internally consistent and the money
*arithmetic* remains clean. But the run as designed cannot reach any of its four
stated success criteria, because everything downstream of a settlement is gated on
a state the INR rail cannot produce in an automated run. Separately, there is a
**seventh instance of the recurring root cause**, in the fix that closed the sixth.

---

## 1. CRITICAL — nothing downstream of a settlement ever runs

`src/exchange/service.py:205`, `src/exchange/agents/broker.py:373`,
`src/exchange/house/agent.py:44`

`execute_match` gates `_record_fill` and `_mint_earned` on
`settlement.status == SettlementStatus.COMPLETED`. `Broker.close` gates
`record_deal`, `tree.checkpoint` and `subconscious.consolidate` on the same thing.
`HouseAgent.observe` counts only `SETTLEMENT_COMPLETED`.

The project's own probe (`docs/razorpay-test-mode-findings.md`, and §3.1 of
`learnings_tradeoffs.md`) establishes that **a payment cannot be created
server-side**, so `_await_capture` always returns `None` and every INR settlement in
a fully automated run stays `PENDING`. That single fact is recorded. What is not
recorded anywhere is the size of its blast radius. Measured, one honest trade
through the real broker path against a client that never captures:

```
verdict            : ALLOW
settlement status  : PENDING

ORDER_FILLED       : 0     <- orders never deplete
POINTS_MINTED      : 0     <- nothing ever earns points
LESSON_CONSOLIDATED: 0     <- the Subconscious never runs
ask still open     : True, qty 1000 (unchanged)
confidence(seller) : 0.0   <- the trial cap binds identically forever

HouseAgent.observe : []
privacy verdict    : PrivacyVerdict(allowed=False, 'derived from 0 merchants,
                     below the floor of 25', k=0)
lot minted         : None
PRIVACY_REFUSED    : 1

  re-match pass 1: 1 candidate(s) on the same untouched ask
  re-match pass 2: 1 candidate(s) on the same untouched ask
  re-match pass 3: 1 candidate(s) on the same untouched ask
```

Map that against `docs/superpowers/specs/2026-08-25-market-run-design.md`'s four
properties, each of which it calls a failed run if absent:

| Required | What actually happens |
|---|---|
| 25 merchants settle a real trade | they settle, all `PENDING`; `observe()` returns `[]` |
| the house agent finds a real pattern | privacy floor refuses at `k=0`; no lot is ever minted |
| an auction clears with real bids and moves points | no points are ever minted, so nobody can bid |
| the failure path occurs on real data | `reconcile` raises `Drift` only for `local PENDING / remote captured`, which needs a capture |

Two further consequences worth naming separately:

- **Orders are never depleted, so the book only grows and the same inventory
  re-matches indefinitely.** This is BUG-9's re-settlement hazard, alive again by a
  different route — `ORDER_FILLED` exists and is simply never reached. Over an
  hours-long run every merchant's ask stays at full qty forever, which also means
  `find_candidates` scans a monotonically growing book.
- **`ContextTree.checkpoint` is only called in the same COMPLETED branch**
  (`broker.py:380`), so no broker ever checkpoints. `SubAgent.act`
  (`subagents.py:56`) materialises the whole chain from the nearest checkpoint on
  every call and `render`s every accumulated fact into the prompt. Prompt size
  therefore grows linearly with the number of agent actions and total token spend
  grows quadratically across the run — against a design that budgets $20–25.

**What I would change.** This is a design decision, not a patch, and it has to be
made before the runner is written. Either (a) the runner drives the payment links
the rail already creates (`inr.py:78-84` records `short_url`) so captures genuinely
land, or (b) the "delivered" signal is decoupled from `COMPLETED` — e.g. mint,
fill and consolidate at `SETTLEMENT_INITIATED` for the points/inventory paths while
`observe()` and `record_deal` keep waiting for a capture. Whichever is chosen,
the run needs at least one path to a captured payment or three of its four goals
are unreachable. Do not let this be discovered on day 9.

## 2. CRITICAL — the seventh instance of the recurring root cause

`src/exchange/agents/broker.py:218-241` (`_posted_bid_limit`), reached from
`:269` (`_refuse_above_posted_limit`)

*A value the checker must be authoritative about, supplied by the party it
constrains.* Here it is again, and it is in the code that fixed BUG-26.

`_refuse_above_posted_limit` is the only bound between a model-driven negotiation
and the buyer's own published ceiling. The ceiling comes from `_posted_bid_limit`,
which scans the log for `ORDER_POSTED` with `order_id == match.bid_order_id` and
returns its `limit_price`. **`match` is handed in by the party being bound**, and
`_posted_bid_limit` performs no check at all on the row it lands on: not that the
order is a `Side.BID`, not that its `actor_id` is this merchant.

Its sibling one file over, `Exchange._counterparty_ask_price` (`service.py:274-325`),
was given exactly the four checks this needs, with a docstring stating the general
rule:

> *"Reading an authoritative log at a row the party being paid gets to name is the
> same defect as taking the figure from the argument, with one extra hop."*

The rule was written for the ask side and never asked of the bid side — the same
shape as BUG-24, where the `rolling_spend` reasoning sat one field above
`actor_status` and was never generalised.

Reproduced against the merged source. Buyer publishes a `BID` at `limit_price=2000`;
seller publishes an `ASK` at `limit_price=9000`. The buyer builds a `Match` whose
`bid_order_id` names **the seller's ask**:

```
CONTROL  bid_order_id = own BID(limit 2000), agreed 5000
        -> DENY | Agreed price 5000 exceeds the limit 2000 posted on bid ord_...
        -> settlement: None

EXPLOIT  bid_order_id = the SELLER's ASK(limit 9000), agreed 5000
        -> ALLOW | Within all configured limits
        -> settlement: PENDING amount 250000

_posted_bid_limit returned: 9000 for an order m_buyer never posted
                            and which is not a BID

Buyer published ceiling : 2000/unit -> 50 units = 100000 paise max
Actually settled        : 250000 paise
assert_invariants       : []
```

That is BUG-26's own failure scenario, verbatim — *"a settlement above the order's
own ceiling, with no event explaining the difference"* — reachable through the
check written to prevent it, with every invariant reporting clean.

**Second effect, same root.** `_record_fill` (`service.py:397-409`) writes
`ORDER_FILLED` for `match.bid_order_id` attributed to `buyer_id`. A `bid_order_id`
naming another merchant's order therefore depletes a stranger's inventory in the
buyer's name. Unreachable today only because §1 stops `_record_fill` running at all.

**The comment is also false**, which on this project is a finding in its own right.
`broker.py:222-226` claims *"as everywhere else here, the authoritative figure comes
from the log rather than from whoever is asking to spend against it."* The figure
comes from the log; **the row does not**, and the row is the whole question.

**Fix.** Read it from `self._exchange.state().posted_orders.get(bid_order_id)` — the
projection already resolves most-recent-wins identically, which is what
`_counterparty_ask_price` uses — and apply the two missing checks: `posted.side ==
Side.BID` and `posted.actor_id == self.actor_id`. Refuse, do not clamp, on either,
consistent with the existing `limit is None` branch. Fixing it this way also
removes the full-log scan in §7 as a side effect.

**Test gap that let it through.** `tests/test_broker.py:439-575` has eight tests on
this path and they are good tests — but every one passes `bid_order_id` equal to the
broker's own posted bid, so none of them asks whose order the row belongs to. The
suite pins every property the code claims; the code claims the wrong property.

## 3. HIGH — a Razorpay error on the capture poll kills the run and leaves an ALLOW unresolved

`src/exchange/rails/inr.py:133-141`

`order.create` is wrapped (`:53`) and records `SETTLEMENT_FAILED`. `payment_link.create`
is wrapped (`:85`). `_await_capture`'s `self._client.order.payments(...)` is the one
Razorpay call in `settle()` with no `try/except`, and it runs **after**
`SETTLEMENT_INITIATED` is written. Reproduced:

```
execute_match RAISED: RuntimeError 429 Too Many Requests
log now holds: ['MATCH_PROPOSED', 'POLICY_DECIDED', 'SETTLEMENT_INITIATED']
```

An `ALLOW` with no settlement outcome — precisely the hole BUG-7 was filed to close,
reopened on the other rail. And the run dies. With `poll_attempts=3` (the default)
this call is made **three times per settlement**; 300 settlements is 900 chances to
hit a rate limit. The market-run design names Razorpay rate limits as a known
unknown and requires *"a rejected call as a settlement failure the accountant can
see, never a crash that loses the run"* — that requirement is not met today.

**Fix.** Wrap the poll. A failed poll is not a failed settlement (the order exists
and is payable), so the honest outcome is to stop polling, record the reason in the
`SETTLEMENT_INITIATED` payload or a follow-on event, and return `PENDING` — which
`reconcile` already handles correctly.

## 4. HIGH — `negotiate()`'s only backstop is a token count the provider may not send

`src/exchange/agents/negotiation.py:124`, `src/exchange/llm/openai_compat.py:85-86`

`_rounds` terminates on agreement, a walk, a stall, or `spent >= token_budget`.
`spent` accumulates `response.input_tokens + response.output_tokens`, and
`openai_compat` defaults both to `0` when `usage` is absent
(`getattr(usage, "prompt_tokens", 0) if usage else 0`). An unparseable reply
`continue`s without appending an offer, so `gap_stalled` can never fire on that
path either. Result:

```
usage reported,   unparseable replies: terminated after    67 calls -> token budget exhausted
usage MISSING,    unparseable replies: DID NOT TERMINATE -- still going after 5000 model calls
usage MISSING,    normal haggling:     terminated after     2 calls -> agreed
```

There is no round cap by design, and `config.MAX_NEGOTIATION_ROUNDS` was deleted for
good reasons. But the design document is explicit that *"a runner that can spend an
unbounded amount on model calls would be the same defect in a different currency"*,
and the sole bound is a figure the provider supplies. DeepSeek does return `usage`;
a gateway, a proxy, or a future streaming path need not.

Note also the number in the middle column: **67 model calls for one degenerate
negotiation**, against a whole-run budget of 700–900. A handful of off-format
negotiations blows the cost estimate on its own. `llama3.2` already showed format
failures (BUG-13); this is what that costs now.

**Fix.** Add a hard call counter to `_rounds` as a backstop beneath the token
budget, ending with an explicit `ended_reason`, and treat a zero-token response as a
budget charge rather than free.

Related, same file: `negotiate` records `NEGOTIATION_ENDED` on a provider exception
and then **re-raises** (`:102-105`). Recording it is right. Re-raising means every
caller must catch, and no caller in the repo does — verified for `scripts/two_brokers.py:89`.
The runner must, and that is worth writing into the runner's brief rather than
leaving to be discovered.

## 5. HIGH — a resumed run cannot match anything listed by a previous run

`src/exchange/service.py:77`, `:101-109`

`Exchange._indexed` is a plain list on the instance, and `HybridIndex` holds its
documents in memory. Neither is folded from the log. Every other read path in the
system is a projection; the retrieval index is not. The design requires resumability
in as many words — *"on start, fold the log, skip what is already done, continue"*.

```
RUN 1  index size: 1   candidates found: 1

RUN 2  (same database, fresh process)
       assets in projection : ['ast_mailers']
       open ASK orders      : ['ord_e732beeb5238']
       index size           : 0      <- NOT folded from the log
       candidates found     : 0      <- the ask is unmatchable
```

The ask is feasible, in the book, and in `state().assets`. `find_candidates` filters
on `ask.asset_ref in assets` (which passes) and then intersects with
`index.search(...)` (which is empty), so it returns nothing — **silently**. A
resumed run reads as "the market had no supply", which is the worst possible
presentation of a bug: it looks like an economics result.

**Fix.** Rebuild the index from `state().assets` in `Exchange.__init__` (or make
`list_asset` idempotent and have the runner re-list on start). The projection
already holds everything needed.

## 6. HIGH — `reconcile()` re-checks every settlement ever recorded, over the network, unguarded

`src/exchange/house/accountant.py:130`, `:148-158`

`reconcile` reads the whole log and issues `self._client.order.payments(order_id)`
for **every `SETTLEMENT_INITIATED` in it**, on every call, with no error handling and
no watermark. Measured:

```
settlements in log         : 12
order.payments() calls     : 12   (1st reconcile)
order.payments() calls     : 12   (2nd reconcile: re-checks all history)

reconcile() raised         : RuntimeError 429 Too Many Requests
```

R reconciliation passes over N settlements cost R×N Razorpay round-trips, and on a
resumed or re-tuned run N includes every settlement from every previous run. If the
runner reconciles per round — which is the natural design, since the failure demo
depends on the accountant noticing — that is quadratic in network calls against the
one external service whose rate limits the design lists as unknown. And a single
429 anywhere in the sweep raises out of `reconcile()` with only a partial pass
recorded.

Local cost is linear and acceptable on its own; it is the network fan-out that
bites:

```
 log events |  assert_invariants |    reconcile |  razorpay calls
        593 |             3.4 ms |       3.8 ms |              30
       2093 |            12.8 ms |       8.7 ms |              30
       8093 |            51.2 ms |      31.9 ms |              30
      20093 |           138.7 ms |      84.1 ms |              30
```

**Fix.** Skip settlements already `COMPLETED` locally *and* already contained (both
sets are computed at `:131-143` and then not used to prune the loop), keep a
watermark seq so a pass only checks what is new, and wrap the remote call so one
rejected request degrades that settlement's check rather than the whole run.

## 7. MEDIUM — the one full-log scan left on the money path, and the cost test that cannot see it

`src/exchange/agents/broker.py:235`, `tests/test_projection_cost.py:145-176`

`perf-fold-report.md` reports the per-trade curve as flat — *"3.0 → 3.5 → 3.9 ms
across a 20x range of log size"* — and `test_projection_cost.py`'s docstring claims
the tests *"fail if any call site starts re-scanning again, including one added
later by someone who has not read this file."*

Both measure `Exchange.execute_match`. The production money path is
`Broker.close`, which calls `_posted_bid_limit` → `log.read_all()` **before**
`execute_match` is reached. `_trade()` in the cost harness (`:145`) calls
`ex.execute_match` directly, so `Broker.close` — and therefore the only remaining
scan — is outside every one of those tests. That is why it survived the perf pass.

Measured on this machine (medians of 7, projection pre-warmed):

```
 log events |  _posted_bid_limit |  projection lookup |  Broker.close
        225 |            0.71 ms |          0.0088 ms |       1.76 ms
       1025 |            3.64 ms |          0.0050 ms |       5.21 ms
       5025 |           18.77 ms |          0.0052 ms |      20.37 ms
      20025 |           85.87 ms |          0.0056 ms |      87.22 ms
```

`_posted_bid_limit` is 98% of `Broker.close` at 20k events and grows linearly;
`state().posted_orders.get(...)`, which answers the identical question with the
identical most-recent-wins rule, is flat at ~0.005 ms.

Honest magnitude: ~300 closes over a 15k-event run costs roughly 10 s of wall
clock — real but not the thing that ruins the run. It matters because (a) it is
quadratic per run and compounds across tuning re-runs against a growing persistent
log, and (b) the fix is the same one-line change §2 already requires. Extend
`_rows_for_one_trade` to go through `Broker.close` so the harness covers the path it
claims to.

## 8. MEDIUM — the cumulative spend cap exhausts around the third tuning run

`src/exchange/service.py:365-386`, `src/exchange/policy.py:57`

Listed as known and accepted, and I am reporting it only because the run's own shape
makes it materially worse than recorded. `rolling_window_cap = 10_000_000` paise,
cumulative and never decaying, per actor per currency, over **one persistent log**
that the design says will be **re-run repeatedly for tuning**:

```
typical trade 1940 x 200:   388000 paise ->  25 trades per merchant EVER
small         1940 x  50:    97000 paise -> 103 trades per merchant EVER
```

At ~10 trades per merchant per run, the cap binds during run 3 and every subsequent
trade returns a correct, well-reasoned `DENY` that reads exactly like a gate bug.
Wave D's review flagged the same arithmetic for `two_brokers.py` at ~11 runs; at 30
merchants it arrives sooner and looks like an economics finding. **Fix:** land the
time window the field already documents as owed, or give each tuning run a fresh
database and accept that resumption then means something narrower.

## 9. MEDIUM — a merchant can write unlimited `POLICY_DECIDED` under one `action_ref`

`src/exchange/agents/broker.py:290-321`

`execute_match` refuses a second trip through the gate (`service.py:139`) because
`assert_invariants` joins settlements to decisions on `match_id` and that join is
only sound while the id is unique. `_log_refusal` writes a `POLICY_DECIDED` and
never consults `_already_decided`:

```
close() x3 on the same Match above the posted limit
POLICY_DECIDED events for match mch_c880371b : 3
all sharing one action_ref: True
assert_invariants: []
```

This is BUG-25's hole from the other side: the merchant's own refusals manufacture
the duplicate `action_ref` the join exists to prevent. It also works in the opposite
direction — a single `_log_refusal` poisons `decided_action_refs`, so a corrected
retry of that same `Match` raises `ValueError` out of `close()` rather than
returning a decision (noted as an ergonomic hazard in `re-review.md` §3; a
round-based runner retrying a match is exactly the caller that hits it).

**Fix.** Refuse a second refusal on a spent `match_id`, and add a
`duplicate_decision` invariant — a `match_id` carrying more than one
`POLICY_DECIDED` is itself worth naming, whoever wrote them.

## 10. MEDIUM — `Broker.choose` crashes on a shortlist entry that left the book

`src/exchange/agents/broker.py:121`

seller = self._exchange.state().open_orders[m.ask_order_id].actor_id

The shortlist comes from a `state()` snapshot taken in `find_supply`; this indexes

## 11. LOW — `list_asset` re-embeds the entire catalogue on every listing

`src/exchange/service.py:108-109`, `src/exchange/retrieval.py:65-73`

`HybridIndex.index()` replaces its corpus, rebuilds BM25 and re-embeds every text.
`list_asset` calls it with the whole accumulated list each time:

```
90 listings -> 90 index rebuilds, 4095 texts embedded
(linear would be 90; this is n(n+1)/2 = 4095)
```

With `default_embedder()` (model2vec, real weights) rather than the stub used here,
30 merchants seeding their inventories pays this at startup. Bounded and one-off if
all listing happens up front; genuinely quadratic if the runner lists during rounds.
**Fix:** an `add()` that appends and re-fits once, or batch the seeding.

knows. `scripts/two_brokers.py:49` already passes `poll_attempts=1, poll_interval=0`;

reviews, so these are findings rather than style:

- **`broker.py:222-226`** — *"as everywhere else here, the authoritative figure comes

  added to `__init__` surfaces as an `AttributeError` at the first model call of the

Nothing else in `src/` reads as dead. The deletions listed in `re-review.md`
(`CreditLedgerEntry`, `RelationshipEdge`, `config.K_MIN`, `MAX_NEGOTIATION_ROUNDS`,
`Broker._provider`) are genuinely gone.

## Areas that are clean

One line each, because the review is otherwise long.

- **Money arithmetic.** Integer minor units throughout; no float touches an amount.
  `points_for_settlement`'s `min(margin, amount)` bound and the `amount <= 0` floor
  in both `policy.evaluate` and `points_for_settlement` are correct and belt-and-braces.
- **`fold` / `fold_from`.** Every branch reads defensively; I could not construct an
  event that makes it raise. `ACTOR_FROZEN`-creates / `ACTOR_RESUMED`-does-not is
  right and its docstring's reasoning is right.
- **`_counterparty_ask_price`.** All four checks present and correct; this is the
  model §2 should be fixed against.
- **`CreditRail`.** The balance lookup is a function of the payer the rail itself
  identified, `settle()` takes no balance, and it logs `SETTLEMENT_FAILED` before
  raising. Clean.
- **Privacy floor.** Counts distinct merchants, re-checked independently in
  `mint_lot`, refusal logged with its `k`.
- **Second-price mechanics and `Bid.parsed`.** Unreadable replies are excluded before
  the two-bid minimum and named in the reason. Correct.
- **`Accountant.repair`.** Still the strongest code on the branch: refuses an
  `UnbackedCompletion` by type, refuses a null payment id, idempotent by refusal.
- **Id generation.** `new_id` is uuid4-based, so nothing in `src/` can collide across
  runs in a shared log. The hard-coded ids that remain are in `scripts/`, which the
  runner replaces.

## The three things to fix before the market run

1. **§1 — decide how an INR settlement reaches `COMPLETED`, and wire it.** Without
   it the run produces no fills, no points, no lots, no auction, no relationship
   ratchet and no failure demo — three of the four success criteria are unreachable
   and the fourth is unreadable. This is a design decision and it belongs before the
   runner is written, not during it.
2. **§2 — give `_posted_bid_limit` the ownership checks its sibling already has**,
   reading from `state().posted_orders`. It is the seventh instance of the root
   cause, it defeats the fix for the sixth, and the same edit removes §7's scan. Add
   the test nobody wrote: *the row must be this merchant's own BID*.
3. **§3 + §4 — make the two failures a long run will actually hit into records
   rather than exceptions.** Wrap `_await_capture`'s Razorpay call so a 429 leaves a
   `PENDING` settlement instead of a dead process, and give `negotiate` a hard call
   backstop beneath a token budget the provider is trusted to report. §6's watermark
   belongs in the same pass, since it is the other place one rejected Razorpay call
   ends the run.
